# Style rules for manquehue_chip

Rules for every file in this repository. Each rule says what to do. The sources are listed at the end.

## 1. Principles
1. One fact, one place. A value that two scripts need (a corner, a library, a clock uncertainty) is defined in `config/` and read from there. Never copy it.
2. Folders follow the flow: `sim`, `impl`, `signoff`, `release`, `fpga`. A folder holds one stage, a file does one job.
3. `make` is the interface. A person runs `make <target>`, not a script. A script can still run alone for debugging.
4. Results go to `outputs/<run>/`, tool scratch to `work/`. Nothing is written to the repository root.
5. Remove a trap in code, do not document it. A README lists only the traps that code cannot remove.

## 2. Files and names
- Names are `lower_case_with_underscores`, and say what the file does or holds: `scan_sta.sh`, `corners.tcl`.
- Implementation steps keep their order number: `01_read_rtl.tcl` to `06_finish.tcl`. Nothing else is numbered.
- Each sign-off check has one entry script, named after the check: `scripts/signoff/pv/drc.sh`, `sta/sta.sh`. Its options are in the script, or in a `settings.sh` that the scripts of one folder share. Files that are only sourced have no `run` in their name.
- Generated files are never edited by hand, and start with a `GENERATED by <script>` line.
- A file holds one job. When a file needs a table of contents, split it.

## 3. Which language
| Language | Use it for | Do not use it for |
|---|---|---|
| Make | targets, their order and their variables (`RUN=`, `CORNER=`) | recipes longer than about 5 lines: put them in a script |
| Bash | glue: set up, call a tool, collect its result. Under about 100 lines | parsing reports, arithmetic, data tables: use Python |
| Tcl | everything inside an EDA tool (FC, PT, FM, ICV, TestMAX, KLayout uses Python) | logic outside a tool |
| Python 3.6+ | parsing, reports, generators, small checks | tool command sequences |
| SystemVerilog | RTL and testbenches, lowRISC style guide | |

Python stays 3.6-compatible because Rocky's system Python is 3.6.

## 4. File header
Every file starts with at most five comment lines:
```
# <one line: what this file does>
# Author: Nicolás Villegas - Universidad de los Andes, Chile
# usage: <command line>                     (runnable files only)
# in:  <files and env variables it reads>
# out: <files it writes>
```
No banners (`####` boxes). A proc or function gets one line on what it does and what it returns, when the name does not already say it.

## 5. Shared knowledge (`config/`)
- `config/*.tcl` hold only `set NAME value` lines and comments. No logic, no `if`, no procs.
  - `design.tcl`: paths, design name, macro size and position
  - `corners.tcl`: corner names, libraries, RC corners and SPEF temperature per corner
  - `clocks.tcl`: periods, IO budgets, clock uncertainty before and after CTS
  - `sdc/`: the constraint sources (`mode_func`, `mode_scan`, design rules)
- Tcl reads them with `source`. Bash reads them through one helper, `scripts/lib/config.py` (`sh`, `get NAME`). The helper is Python because Rocky has no `tclsh`. Make does not read them: the scripts do.

## 6. Step scripts (implementation and sign-off)
Same skeleton in every step, as in the Synopsys FC Reference Methodology:
1. source `config/` and the shared procs
2. open the input (library, netlist, previous step)
3. optional user hook (`<step>_pre.tcl`), only where we need one
4. the step
5. reports into `outputs/<run>/<step>/reports/`
6. save, then write `summary.txt`

Every check writes `outputs/<run>/checks/<check>/summary.txt`: `key: value` lines, the last line `status: PASS` or `status: FAIL`. `make report` reads all of them.

## 7. Makefile
- One `Makefile` at the root and one `module.mk` per stage folder, included by the root Makefile. No recursive `$(MAKE)`.
- Every target a person uses has a `## <description>` on its line. `make help` lists them. `make help-all` also lists the `### ` (expert) targets. `##@ <title>` starts a section.
- A recipe calls one script. The defaults of the options are in the script (`VAR=${VAR-default}`), and Make passes the command-line values on.
- Tool runs `cd` into `work/<step>/`, so tool files (`*.svf`, `fc_command.log`) never reach the root.

## 8. Comments
- A comment says why, or what is not obvious. It does not repeat the code.
- Write comments and READMEs in short, plain sentences: active voice, one idea per sentence, no semicolons, no em dashes.
- A README is at most about 15 lines: what the stage is for, the commands, inputs to outputs, and the traps code cannot remove.

## 9. Linters (`make lint`)
| Files | Tool | Where it comes from |
|---|---|---|
| `.sv`, `.v` (our RTL and testbenches, not vendored IP) | `verible-verilog-lint` | installed on Rocky |
| `.sh` | `shellcheck` | nix |
| `.tcl`, `.sdc` | `tclint`, `tclfmt` | nix (needs Python 3.8+) |
| `.py` | `ruff` | nix |

Phase 1 lints only the files a PR touches. Phase 2 cleans each stage completely.
